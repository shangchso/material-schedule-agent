# 05 复盘：最难问题、学习收获与下一步

## 1. 最难的问题

最难的不是写工具，而是**状态驱动的决策闭环**：Agent 每一步都要根据上一轮工具观察结果选择不同动作，尤其是三个边界——

1. 时段冲突后，替代时段必须停下来等用户确认，不能替用户拍板。
2. 重复提交要靠幂等键（素材 ID）拦截，而不是简单报错。
3. 保存成功/失败的状态必须回传到决策层，否则会出现重复保存或虚报成功。

实际开发中也确实在第 3 点上暴露了 bug，修复后才理解 ReAct 循环里"状态"是唯一的决策依据。

## 2. 学习收获

- 理解了 ReAct 模式与写死流程的区别：动作由模型依据观察结果动态选择，而不是预设的固定分支。
- 掌握了 Agent 工程的基本分层：工具层、决策模型层、状态与循环控制层、入口与测试。
- 体会到 Trace 对评审和调试的价值：每一步的入参、观察与决策依据可直接复盘。
- 建立了安全边界意识：不越权发布、不修改硬性要求、不虚报成功。

## 3. 下一步改进

1. 接入真实大模型验证决策质量，对比 MockLLM 与真实模型在冲突场景下的动作差异。
2. 给草稿增加持久化存储，并保留运行期状态重置能力。
3. 扩展批量素材处理，处理多个素材之间的时段竞争。
4. 补充更多异常注入（网络超时、规则文件缺失），增强健壮性。

## 4. 实际用时

按题目要求记录：核心链路（工具 + ReAct 循环 + CLI + 验证）在约 3 小时量级完成；界面、线上部署、多 Agent、生产级 Runtime 按题目说明未投入。
